= Git factory

Utilities for creating in-memory JGit repositories programmatically, primarily for use in tests.

== Alternatives
Eclipse jgit provides TestRepository that wraps an existing repository and permits to create commits on it.

== Persisting repositories
FactoGitNew permits to create an in memory repository.
This can be then persisted by the caller by copying it to a FileRepository.
This library does not provide direct support for this: it is not considered within its scope. But it should not be very painful to implement through Eclipse jgit.

== `FastImporter`: fast-export format coverage
`FastImporter` parses `git fast-export` output into an `InMemoryRepository`. It is tested against blobs, multi-commit chains, nested/multi-level directories, executable files, symlinks, gitlinks, merge commits, multiple branches, annotated tags, lightweight tags and branch deletion via `reset`, `from`/`merge` resolved via mark, branch name, or any other JGit-recognized revision expression, distinct author/committer identities, the `encoding` header, non-ASCII content, quoted/escaped paths (including paths containing a space), git's directory-vs-file tree sort order, and patch-style `M`/`D`/`R`/`C` operations (see `FastImporterTests` and the fixtures under `src/test/resources/…/*.fast-export`).

It does not cover the full `git fast-import` stream format. Constructs outside that coverage fail fast with a clear `IllegalStateException` rather than being silently ignored or mis-parsed — verified by dedicated tests (`test*FailsFast` in `FastImporterTests`) that assert each one throws instead of silently producing an incomplete or wrong repository:

* *Not supported, and rejected immediately:* `filemodify … inline` (git fast-export always uses a separate `blob` command instead), `notemodify`/git-notes (any `N` line), `alias`, shorthand file modes (`644` vs `100644`, rejected rather than silently turned into a bogus tree entry), the delimited `data <<EOF` form (only `data <length>` is supported, which is what `git fast-export` always emits), and any other top-level or file-change command this importer doesn't recognize (e.g. `ls`, `get-mark`, `cat-blob`) — previously these were silently dropped.
* *Harmlessly ignored, by design:* `checkpoint`, `progress`, `done`, `feature`, `option`, and stream comments (`#…`) — these carry no information relevant to the resulting repository content, so ignoring them cannot produce a wrong result.
* *`original-oid` and an omitted `author` line* aren't explicitly recognized, but already fail immediately with a "got: ..." message from the surrounding mandatory-field parsing (e.g. expecting `author`/`data` and finding something else) — correct in effect, though the message doesn't name the specific unsupported construct.

== Built-in DAG fixtures
`FastImporter.single()`, `FastImporter.dual()`, `FastImporter.sub()`, and `FastImporter.linked()` build ready-made repositories from `.fast-export` files bundled under `src/main/resources/…`, reproducing the topologies of the deprecated `FactoGit#setBasicDag()`/`setSubDag()`/`setLinkedDag()` and of `JGit#createBasicRepo(Repository)` (single commit with two files; a 2-commit line growing from one file to two; a 3-commit line ending in a subdirectory; a 4-commit line exercising relative/absolute/cyclic/dangling symlinks). Content matches the legacy fixtures commit-by-commit (verified by `LegacyDagFixturesTests`, modulo a trailing newline the legacy `Files.writeString` calls don't add); identities and timestamps are deterministic fixed values instead of the legacy empty-identity/current-time defaults, since those were incidental, not part of the fixture's shape.

== Status of the deprecated `FactoGit` and `JGit` classes
`FactoGit` and `JGit` predate `FactoGitNew`/`FastImporter` and are marked `@Deprecated`. Whether they can be deleted was checked against every consumer of this library findable under the parent `Git/` folder (and, for safety, the whole `Programmation/Java` tree): `GitJFS` and `GitJFS filter` are the only two. All uses of `FactoGit`/`JGit` in those two projects are confined to test code (never `src/main`), across 33 call sites in 7 test files.

* *`FactoGit` is safe to remove.* Every use is the built-in-fixture mode (`FactoGit.empty(); facto.setSubDag(); facto.build();`, 6 occurrences), none of its general-purpose features (custom `Graph<Path>`, `setIdentConstant`/`setIdentIncreasing`, `setLinks`, the `createRepository(...)` overloads) are exercised by these consumers. `FastImporter.sub()`/`single()`/`linked()` are drop-in, more elegant replacements (one-liners instead of three statements), already proven equivalent by `LegacyDagFixturesTests`.
* *`JGit` still covers one capability nothing else in this library offers: populating a caller-supplied `Repository`* — including a plain on-disk `FileRepository`. `FactoGitNew.repo()` and `FastImporter.importRepository(...)` always construct and return their own fresh `InMemoryRepository`; there is no overload that writes into a repository the caller already built, and `GitCloner` only clones from a remote `GitUri`. Three call sites in `GitJFS` rely on this, each for a different reason:
+
[source,java]
----
try (Repository repo = new FileRepository(dir.toFile())) {
  JGit.createBasicRepo(repo);
}
----
+
`GitFileSystemCreationAndUriTests#initGitRepo()` builds this way because every other test in that class then reopens `dir` through the path-based `gitjfs://FILE` URI scheme / `GitFileSystemProvider#newFileSystemFromGitDir(Path)` — a genuinely different entry point from `newFileSystemFromDfsRepository(DfsRepository)`, which the same test class already covers separately, in memory (`testMemRepo`/`testDoubleMemRepo`). `GitReadTests#testFindSmall()` does the same, closing and reopening the repository from disk in between. And `GitReadTests` has a `main()` demo method building a linked-commit repo at a fixed path (`/tmp/ploum/.git`) so a developer can inspect the result by hand after the JVM exits — a case an in-memory repository can't satisfy for yet another reason: nothing survives once the process ends or the repository is closed. Note though that I have my doubts that this uri stuff is correct, it should be reworked anyway.
+
The commit-building step itself is backend-agnostic (`ObjectInserter`/`TreeFormatter`/`RefUpdate` work identically on either backend); what actually forces `FileRepository` in all three cases is that the *result* has to outlive the call and be addressable by `Path`. The decided workaround for this is not to keep `JGit` around, but to build the repository in memory as usual (`FastImporter`/`FactoGitNew`) and separately persist it into the caller's `FileRepository`, per "Persisting repositories" above.
* *The topology gap is closed:* `JGit.createBasicRepo(Repository)` produced two commits (`file1.txt`, then `+file2.txt`), which had no equivalent — `FastImporter.basic()` (now `single()`) was single-commit, matching `FactoGit#setBasicDag()` instead. `FastImporter.dual()` now reproduces that 2-commit topology exactly (verified by `LegacyDagFixturesTests#testDualMatchesLegacy`), so this is no longer a blocker for the `JGit` call sites that only needed the topology, not the "populate an existing `Repository`" capability.
* *Minor remaining friction:* `JGit.createBasicRepo`/`createRepoWithSubDir`/`createRepoWithLink` hand back the created commits as an ordered `ImmutableList<ObjectId>`, which ~27 call sites use directly (`commits.get(n)`). `single()`/`dual()`/`sub()`/`linked()` return only a bare `DfsRepository`; callers must recover the ordered ids themselves (a `RevWalk` with `RevSort.TOPO`/`REVERSE`, or read them back off a constructed `GitFileSystem`'s `graph()`, as some consumer tests already do). More code, one more layer of indirection, but not a hard blocker.

Net: `FactoGit` can be deleted now. `JGit`'s remaining obstacle — populating a caller-supplied `Repository` — has a decided workaround (build in memory, persist separately, see above), so it no longer needs to be kept for that reason either; note, though, that the persist step isn't implemented anywhere in this library yet, so removing `JGit` now shifts that work onto each of the three call sites that need it. Neither `GitJFS` nor `GitJFS filter` has been migrated yet: `GitJFS` still references `FastImporter.basic()`/`basic.fast-export` (now renamed to `single()`/`single.fast-export`) and would fail to compile against this version until updated; both still use `FactoGit`/`JGit` in their tests. That migration is intentionally out of scope for this round of changes. `GitJFS filter` also still pins `git-factory 0.0.7`, one release behind this project's `0.0.8-SNAPSHOT`, and should be bumped before migrating.
